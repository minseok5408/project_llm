# ADR 0019: 대화 제어·화면 수명·저장소·실행 의존성 분리

- 날짜: 2026-09-12
- 상태: 구현·통합 검사 완료
- 범위: 기존 기능의 역할 분리. API·DB 스키마·환경 설정 변경 없음

## 배경

파일 첨부·질문 카드·검색·언어 정책을 추가하면서 대화 세션과 Workbench에 서로 다른 수명의 상태와 부수효과가 모였다. 저장소는 권한·커서·메시지·파일 삭제까지 조합했고, 검색·문맥 준비 단계는 생성 서비스 전체에 의존했다. 현재 기능을 유지하면서 변경 영향과 비동기 정리 책임을 확인할 수 있도록 경계를 나눈다.

## 프런트의 제어와 비동기 처리

`ConversationSession`은 초안·대화 목록·사용자 요청과 하위 처리 객체를 조합한다. 파일 조회·업로드·변경·폴링은 `ConversationFiles`, 생성 SSE 연결·재연결·중단은 `GenerationStream`이 맡는다. 하위 객체에는 필요한 요청·현재 상태 조회·변경 반영·취소 신호와 완료 콜백만 전달한다.

`generation-events.ts`의 상태 변환은 원본 상태를 변경하지 않고 검증한 현재 생성의 이벤트만 변경분과 재생 커서로 반환한다. 네트워크 호출과 종료 후 재조회는 스트림 제어에 남긴다. 대화·메시지·생성 자료형은 `conversation-types.ts`, 여러 기능에서 공유하는 요청 자료형·API 오류 처리는 `lib/http.ts`로 옮긴다. 기존 세션의 공개 메서드와 자료형 import는 유지한다.

초안·질문 입력과 다른 대화의 진행 작업, 마지막 이벤트 이후 재연결·본문 중복 방지, 파일 조회 경합과 계정 종료 시 취소를 보존한다. 이 분리로 파일·기억·네트워크 기능이 대화 세션 구현의 내부 오류 처리에 의존하지 않게 한다.

## Workbench와 브라우저 수명

Workbench에는 화면 조합, 전송 가능 여부와 사용자 행동 연결을 남긴다. 다음 여섯 훅이 각자의 등록·해제를 소유한다.

| 훅 | 책임 |
| --- | --- |
| `use-chat-session` | 계정별 저장소·주소 이동·뒤로가기·화면 복귀 갱신 |
| `use-chat-scroll` | 최신 답변 따라가기·사용자 스크롤·이전 메시지 앵커 복원 |
| `use-model-status` | 모델 상태 폴링과 요청 취소·늦은 응답 폐기 |
| `use-web-mcp` | 최신 전송 함수 연결·도구 등록·화면 종료 시 해제 |
| `use-workbench-menus` | 검색 단축키·외부 클릭·Escape·초점 복귀 |
| `use-reduced-motion` | 모션 설정 구독·해제 |

각 훅은 필요한 값과 동작만 받으며 DOM 이벤트·타이머·도구 등록을 Workbench가 직접 관리하지 않는다. 기존 UI, 입력 가능·전송 차단, 질문 카드·완료 알림을 유지한다. 숨겨 둔 작업·문맥 메뉴와 진행 계획·처리 과정 목록은 다시 표시하지 않는다.

## 저장소와 삭제 서비스

`Repository`는 같은 `RepositoryAccess`를 사용하는 계정·대화·메시지 저장소를 명시적으로 조합한다. 동적 속성 전달을 사용하지 않고 기존 조회·저장 메서드의 인자와 반환 형식을 유지한다. 권한과 잠금은 `access.py`, 검증은 `validation.py`, 커서는 `pagination.py`, DB 오류 변환·비밀값 없는 공통 기록은 `operations.py`가 맡는다.

대화와 파일을 함께 삭제하는 절차는 저장소에서 `ConversationService`로 옮긴다. 서비스가 대화 저장소의 권한·삭제 표시와 `files/deletion.py`의 첨부·검색 조각 제거·원본 삭제 대상 표시를 같은 세션에서 조합한다. 사용자→소속→대화의 기존 잠금 순서를 유지하며 각 저장소·파일 함수는 직접 커밋하지 않는다. API가 성공 후 커밋하고 기존 원본 정리 절차를 호출한다. 같은 트랜잭션의 파일 표시·검색 조각 제거가 실패하면 대화 삭제 표시까지 롤백한다.

## 생성 단계의 실행 계약

`runtime/contracts.py`의 `GenerationJob`은 DB에서 인수하고 준비 단계가 반환하는 작업 스냅샷의 필드를 명시한다. `ModelExecution`은 DB·모델 공급자·설정만 담고 승인·중단·정산 기능은 노출하지 않는다.

worker가 문맥 압축·웹검색·원문과 기억·파일 문맥·질문 카드·답변 실행을 조합한다. 준비 단계는 필요한 실행 의존성을 받으며, 웹검색의 검색 공급자·네트워크 정책은 별도 인자로 전달한다. 단계별 사용량 기록은 DB·설정을 받는 `StepService`에 유지한다. 실제 답변 사용량의 종료 후 한 번 정산과 시스템 계정 면제, 자동 압축의 사용자 비차감 정책은 변경하지 않는다.

## 검증과 적용

검증 범위는 세션의 기존 공개 동작·순수 이벤트 변환, SSE 재연결·계정 종료·파일 경합, Workbench의 SSR·브라우저 이벤트·폴링·도구 해제·스크롤, 저장소 권한·순번·커서와 원자적 삭제, 실행 단계·중단·정산이다. 전체 프런트 171개·백엔드 741개, 격리 DB의 migration 왕복·스키마 비교, TypeScript·lint·포맷·빌드를 통과했다. 확정 결과와 실제 모델·브라우저 검사의 범위는 [개발 현황](../development-status.md)에 기록한다.

새 마이그레이션은 없고 head는 `0016_local_file_rag`, 도메인·관측 테이블은 22개다. 이번 정리에서 실제 개발 DB·`.env`를 변경하거나 별도 개발 서버를 시작하지 않는다. 초기 구조와 기능별 결정은 과거 ADR에 보존하고 현재 경로는 [프로젝트 구조](../../tree.md)를 따른다.
