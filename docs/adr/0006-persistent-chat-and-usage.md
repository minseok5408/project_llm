# ADR 0006: 대화 저장, 영속 생성 작업과 실제 토큰 정산

- 날짜: 2026-09-09
- 상태: 로컬·허용된 같은 Wi-Fi 환경에 적용
- 마이그레이션: `0005_generation_runs` (`0004_auth_sessions` 이후), 취소 정산 기준은 `0007_cancellation_usage`

## 결정과 범위

브라우저의 메모리에만 있던 대화를 PostgreSQL에 저장한다. 로그인한 사용자는 소속 작업 공간의 대화를 조회하고 `/chat/{id}`에서 다시 열 수 있다. 새 요청에는 사용자 메시지 하나와 허용한 생성 옵션만 보내며 모델 문맥은 서버가 구성한다. 이 결정은 ADR 0005의 “채팅 저장과 실제 토큰 정산은 후속”이라는 당시 제한을 갱신한다. 절대 24시간 세션·로컬 HTTP 정책은 유지한다. 공개 가입의 현재 기본값은 `open`이며 로그인·가입·비밀번호 변경의 8~32자 규칙과 가입 후 자동 로그인은 [ADR 0005](0005-authentication-and-24-hour-sessions.md)를 따른다. 일반 회원의 월 무료 20,000토큰은 [ADR 0007](0007-monthly-allowances.md)에서 자동 지급하며 시스템 권한은 자동 부여하지 않는다.

이 ADR의 `0005_generation_runs`에서 `generation_runs`와 `generation_events`를 추가해 당시 도메인 테이블은 12개가 됐다. 현재는 [ADR 0009](0009-context-compaction-and-continuation.md)의 대화 요약까지 13개다. 기존 계정·대화·메시지·토큰 예산·인증 데이터를 유지하는 업그레이드이며 계정이나 예산을 자동 생성하지 않는다. 모델 추론은 기존 로컬 MLX 서버에서 수행한다. API 안의 생성 worker를 별도 프로세스로 분리하는 일은 후속이다.

## 권한과 대화 저장

사용자는 쿠키의 서버 세션으로 결정한다. 목록·단건·메시지·생성 이벤트 조회는 활성 사용자와 활성 작업 공간 소속을 확인한다. 다른 작업 공간의 객체는 `404`로 응답하며 `system` 권한도 소속 검사를 우회하지 않는다. 생성 중단은 본인이 시작한 작업만 허용한다. 제목·고정·보관·삭제는 대화 작성자 또는 작업 공간 owner/admin만 허용한다. 인증된 상태 변경에는 Origin·CSRF를 검사하며 새 대화·생성 경로는 JSON 형식과 미허용 필드를 검증한다.

워크스페이스 목록은 기존 소속만 반환한다. 조회 중 기본 작업 공간을 자동 생성하지 않는다. 대화는 `(last_message_at, id)` 내림차순 커서, 메시지는 대화 안의 순번 커서로 조회한다. 보관과 soft delete를 지원하고 삭제·보관 대화는 일반 목록에서 제외한다. 진행 중 생성이 있는 대화의 보관·삭제는 `409`다. PIN 표시 순서는 프런트가 이미 불러온 목록 안에서 정렬하며 전체 페이지를 아우르는 고정 우선 정렬은 구현하지 않았다.

첫 질문의 앞 60자를 기본 제목으로 쓰며 LLM 자동 제목은 후속이다. `/chat/{id}`로 새로고침하거나 다른 기기에서 로그인해도 저장된 메시지를 복원한다. 로그아웃·세션 만료 때 브라우저 상태를 정리하고, SSE 중에도 세션·소속을 재검사한다. 이벤트 조회는 짧은 DB 세션으로 수행해 연결 전체 동안 pool이나 transaction을 잡아 두지 않는다.

## 승인과 이벤트 계약

대화·작업 공간·자기 사용량 API는 [run.md](../../run.md#저장형-채팅과-생성-api)에 정리했다. 생성 경로는 다음과 같다.

1. `POST /api/v1/conversations/{id}/messages`에 UUID `Idempotency-Key`와 `{content, options:{thinking,max_tokens}}`를 보낸다.
2. 서버가 권한·모델·기존 생성 상태를 확인하고 저장된 요약과 종료된 작업의 사용자 발언·실제 답변에 서버 system prompt와 새 질문을 더한다. 완료·실패·중단·기존 `usage_pending` 작업을 포함하며 빈 placeholder는 제외한다. 미완성 문맥과 이어 쓰기는 [ADR 0009](0009-context-compaction-and-continuation.md)를 따른다.
3. DB transaction 밖에서 모델 서버에 실제 입력 토큰 계산을 요청한다. 압축이 필요하면 최근 원문·현재 질문의 최소 실행 가능성을 먼저 확인하고 단일 worker가 요약한 뒤 최종 문맥·출력 상한을 확정한다. 대기열 승인·사용자·소속·대화 잠금 아래 변경 여부와 예산을 다시 검사한다.
4. 허용량만 기록하는 `deferred` 회계 기록, 사용자 메시지, assistant placeholder, 생성 작업과 최초 이벤트를 하나의 짧은 transaction으로 저장하고 `202`와 ID·events URL을 반환한다. 예산은 예약·차감하지 않으며 완료·중단 후 차감한다. 현재 계약은 [ADR 0008](0008-deferred-charging-and-chat-scroll.md)을 따른다.
5. 같은 사용자·키·내용·옵션은 기존 작업을 반환한다. 완료·취소된 작업도 다시 실행하지 않는다. 같은 키의 다른 요청은 `409`다. 과거 `/api/chat`은 `410`으로 닫는다.

`GET /api/v1/generations/{id}`는 상태를, `/events?after=<id>`는 저장된 이벤트를 반환한다. `after`가 없으면 `Last-Event-ID`, 둘 다 없으면 0부터 재생한다. 이벤트 종류는 `meta`, `delta`, `done`, `error`, `cancelled`이며 생성별 연속된 `id:`를 사용한다. 아직 저장하지 않은 번호를 요청하면 `422`다. 프런트가 진행 작업을 다시 열 때는 0부터 재생하며 DB의 부분 본문과 중복 합치지 않는다.

수신 조각은 약 40ms 또는 4096자 단위로 assistant 본문·이벤트에 함께 저장한다. 브라우저는 받은 텍스트를 한글·이모지가 깨지지 않는 grapheme 단위로 나누어 약 10ms 간격으로 표시한다. 표시 대기가 길어지면 여러 묶음을 함께 표시해 따라잡고, 중단 때는 표시 대기열을 비운다. 모션 감소 설정에서는 타이핑 지연을 생략한다. 저장 원문과 회계는 이 표시 속도와 분리한다.

서버가 받은 숨겨진 reasoning 본문은 저장하거나 표시하지 않는다. reasoning 토큰도 모델의 최종 출력 사용량 또는 서버가 확인한 수신 토큰 수에 포함된다. 오래된 이벤트 정리와 장기 보존 정책은 후속이다.

## 단일 실행자와 대기열

`GENERATION_WORKER_ENABLED=true`가 기본이다. DB를 활성화한 API는 내장 worker 후보를 시작하고 API pool과 별도의 asyncpg 연결로 PostgreSQL advisory lock을 유지한다. 같은 DB를 사용하는 후보 중 한 개만 복구·claim·추론을 수행한다. claim에는 `FOR UPDATE SKIP LOCKED`를 사용한다. 연결이 사라지면 리더 잠금이 풀리고 다음 리더가 기존 running 작업을 먼저 확인한다.

`GENERATION_QUEUE_LIMIT=3`일 때 queued/running 합계 상한은 실행 슬롯을 포함해 4건이며 사용자별·대화별 active 작업은 각각 1건이다. 상한 초과는 스트림 시작 전 `429`와 `Retry-After`로 응답한다. queued 작업은 생성 시각·UUID 순서로 처리한다. 현재 실제 추론은 DB당 1건으로 고정되어 `LLM_MAX_CONCURRENT_GENERATIONS`를 올려도 병렬 worker를 만들지 않는다. 독립 worker 배포, heartbeat·attempt 기록, 더 세밀한 공정성·요청 속도 정책은 후속이다.

## 실제 사용량과 취소·실패

MLX `/v1/responses/input_tokens`를 이용해 생성과 같은 chat template·thinking 설정으로 입력 토큰을 계산한다. 생성 응답은 `stream_options.include_usage=true`로 최종 실제 입력·출력량을 받는다. 입력 계산 API 미지원·계산 실패는 생성 전 `503`이다. 오래된 문맥은 기본 75% 기준으로 자동 요약하며 생성 직전에 실제 입력·출력 상한을 다시 확인한다. 최근 답변·현재 질문만으로도 상한을 넘는 요청은 `422`로 거부한다. 글자 수 제한도 별도로 유지하며 원문을 임의 삭제하지 않는다. 요약 생성 사용량은 별도 시스템 유지 비용으로 기록하고 사용자에게 차감하지 않는다. 요약문을 포함한 실제 답변의 입력·출력은 기존 후정산 정책을 따른다.

**취소 정책 수정(2026-09-09):** running 중단은 대기 중인 HTTP 읽기를 취소하고 모델 응답 연결을 바로 닫는다. 최종 사용량이 도착하기 전 중단한 경우, 서버가 유효한 `logprobs` 항목으로 확인한 누적 출력이 1토큰 이상이면 미리 계산한 입력량과 확인한 출력량만 차감한다. 확인한 출력이 없으면 입력·출력 청구량 모두 0으로 면제한다. 화면의 글자 수로 토큰을 추정하지 않으며 미수신 GPU 사용량을 추가 청구하지 않는 사용자 할인 정책이다. 최종 실제 사용량을 이미 받았다면 그 값을 우선한다.

`token_reservations.usage_basis`는 정상 최종 사용량 `provider`, 사용자 중단의 확인 수신량 `received`, 청구 면제 `waived`를 구분한다. 예약 중에는 NULL이고 반환은 `waived`이며 면제 정산은 입력·출력 0만 허용한다. 같은 정산의 재시도는 입력·출력뿐 아니라 기준도 같아야 한다. `0007_cancellation_usage`는 기존 정산을 `provider`, 반환을 `waived`로 채우며 기존 수치·시각·예산 이력을 바꾸지 않는다.

일반 사용자는 자동 월 무료 예산 또는 우선 적용되는 기간 plan을 사용하며 선택한 예산의 남은 토큰에 맞춰 출력 상한을 줄이며 입력과 최소 답변량도 부족하면 `402`로 거부한다. plan과 무료를 합산하지 않고 여러 작업 공간이 같은 사용자 예산을 공유한다. 생성 승인 기록은 월·플랜 전환 뒤에도 원래 예산에 정산한다. 시스템 계정은 무료 예산 없이 서비스 한도 면제·사용량 기록과 모델 문맥·실행 슬롯 제한을 유지한다. `GET /api/v1/usage`는 자기 계정의 현재 월 예산을 준비한 뒤 선택된 예산의 한도·실사용·예약·잔여량을 반환한다. 로컬 CLI는 유지보수용이며 실제 결제와 공개 관리 화면은 아직 없다.

| 상황                                   | 작업·메시지 처리                                       | 토큰 처리                                                                                            |
| -------------------------------------- | ------------------------------------------------------ | ---------------------------------------------------------------------------------------------------- |
| 정상 완료                              | `completed`, 사용자·assistant 본문 보존                | `provider` 최종 실제량만 차감                                                                        |
| queued 취소                            | `cancelled`, 질문·취소 placeholder 보존                | `waived`, 청구량 0                                                                                   |
| running 중단 요청                      | 이후 답변 표시·저장 중단, 상류 연결을 닫고 `cancelled` | 최종량이 있으면 `provider`; 없으면 `received` 입력+확인 출력 또는 `waived` 0/0으로 정산 후 슬롯 반환 |
| 모델 미실행이 확실한 실패              | `failed`, 질문 보존                                    | `waived`, 청구량 0                                                                                   |
| 생성 후 실패·빈 응답이며 실제량 확인됨 | `failed`, 받은 본문 보존                               | `provider` 확인된 실제량 정산                                                                        |
| 통신 불명·실행자 중단·사용량 불일치    | 후정산은 `failed`, 저장한 부분 본문 보존               | 청구 0으로 종료하고 다음 질문 허용; 이전 사전 예약 방식만 `usage_pending` 유지                       |

브라우저 연결 종료와 로그아웃은 서버 생성의 취소 신호가 아니다. 명시적인 중단 요청만 연결 종료와 수신량 할인 정산을 적용한다. 후정산 요청이 서버 장애로 종료되면 최종량을 확인한 경우에만 차감하고, 최종량을 확인하지 못한 경우에는 무차감 실패로 끝낸다. 신규 리더는 queued 작업을 계속 처리하고 남은 running 작업과 이전의 미정산 deferred 기록을 복구한다. 상세한 복구·호환 정책은 [ADR 0008](0008-deferred-charging-and-chat-scroll.md)을 따른다.

## 검증과 롤백

실제 임시 PostgreSQL에서 migration 왕복·drift, 권한·멱등성·동시 예약, 대화 복원·SSE 재생, worker 선출과 연결 정리를 검사했다. 백엔드 178개(provider 검사 38개 포함)와 프런트 35개 테스트, 빌드·TypeScript·lint·변경 형식 검사를 통과했다. 실제 MLX의 일반/thinking 입력 계산 39/75가 최종 입력량과 일치했다. 브라우저에서는 로그인·생성·실사용 정산(입력 49·출력 4), 새로고침 후 로그인·대화 유지, 제목 수정·고정을 확인했다. 다른 세션 조회와 동일 요청 키의 재전송에서도 메시지·차감 중복이 없었다. 개발 DB에 `0005_generation_runs` 업그레이드와 `alembic check`를 적용했다. 최신 실행 명령은 [run.md](../../run.md#검사)에 있다.

저장·생성 통합 당시에는 진행 중 새로고침의 부분 응답 복원과 기존 수신 완료 후 취소·정산·예약 반환도 실제 MLX로 확인했다. 검증 후 임시 계정과 해당 작업 공간·대화·생성·예산·세션은 모두 정리했다. 이후 도입한 빠른 중단과 표시 정책의 최종 검증 결과는 [TODO](../../todo.md)에 별도로 기록한다.

`0005_generation_runs` 다운그레이드는 생성 작업·이벤트와 멱등 실행 이력을 삭제한다. 기존 메시지·토큰 예약은 남고 미확정 사용량을 자동 해결하지 않는다. 실제 DB에서 이전 코드로 되돌리기 전에는 worker 중단, 진행 작업·예약 확인, 백업·복구 계획이 필요하다. migration 왕복은 임시 테스트 DB에서만 실행한다. 이메일 확인·초대·RLS·결제·장기 회상 품질 평가·불명 사용량 대조가 남아 있으므로 이번 통합을 전체 서비스 운영 준비 완료로 간주하지 않는다.

`0007_cancellation_usage` 다운그레이드는 사용 수치와 예약을 보존하지만 정산 기준 열을 제거한다. 기준별 감사 이력이 필요하면 내려가기 전에 이를 별도로 보존해야 한다.
