# ADR 0005 — 로그인과 24시간 세션

- 상태: 채택
- 날짜: 2026-09-09

## 요구와 범위

로그인한 브라우저는 로그인 시각부터 정확히 24시간 동안 유지한다. 새로고침·상태 확인·채팅으로 만료 시간을 연장하지 않는다. 유효한 세션이 없으면 로그인 화면을 먼저 표시한다. 로그인 여부는 서버가 매 요청에서 확인하며, 채팅 화면만 가리는 방식으로 접근을 허용하지 않는다.

비밀번호 로그인, 일반 가입, 자기 계정 조회, 현재 세션 로그아웃을 제공한다. 사용자 메뉴와 API에서 모든 기기 일괄 로그아웃은 제공하지 않는다. 공개 가입의 현재 기본값은 `SIGNUP_MODE=open`이며 운영자가 `disabled`로 닫을 수 있다. 이메일 확인·초대 가입·이메일 기반 비밀번호 재설정은 후속 작업이다. 일반 가입이 준비된 시스템 계정을 인수하거나 권한을 올릴 수 없다.

**정책 수정(2026-09-09):** 가입 기본값을 `open`으로 변경하고 로그인·가입·비밀번호 설정·변경 모두 8~32자로 제한한다. 가입 화면은 사용자 이름·이메일·비밀번호·확인을 받고 성공하면 절대 24시간 세션을 즉시 발급한다. 채팅에는 로그인 계정의 `display_name`을 표시한다. 가입자는 `member`이며 기본 작업 공간과 [ADR 0007](0007-monthly-allowances.md)의 이번 달 무료 20,000토큰 예산을 함께 준비한다. 시스템 권한은 자동 부여하지 않는다.

## 저장과 만료

`0004_auth_sessions`는 `auth_identities`와 `auth_sessions`를 추가한다. 비밀번호는 Argon2id로 해시하고, 256비트 이상의 무작위 세션 원문은 HttpOnly 쿠키로 전달한다. DB에는 세션의 SHA-256 해시만 저장한다. 클라이언트의 localStorage·sessionStorage에는 인증정보를 저장하지 않는다.

쿠키의 `Max-Age=86400`, `Expires`와 DB의 `expires_at`으로 브라우저 유지와 서버 만료를 함께 처리한다. 브라우저 쿠키를 조작해도 DB 만료를 연장할 수 없다. 계정 비활성화는 다음 요청부터 차단하고, 비밀번호 설정·변경, 일반 계정의 시스템 승격은 기존 세션을 철회한다. 인증에 사용한 DB 세션은 SSE 응답을 보내기 전에 닫는다.

프런트는 시작 시 `/api/v1/auth/me`로 확인한 뒤 채팅을 마운트한다. 401·만료·로그아웃 때 채팅 내용을 제거하고 진행 중인 브라우저 요청을 취소한다. 연결 장애는 재시도 화면으로 구분한다. 서버 재시작 후에도 DB와 브라우저 쿠키가 남아 있으면 잔여 시간 동안 로그인된다. `localhost`와 LAN IP는 서로 다른 쿠키 호스트이므로 각각 최초 로그인이 필요하다.

## 로컬 HTTP와 요청 검증

현재 허용된 로컬·같은 Wi-Fi 접속은 HTTP다. 따라서 기본 `AUTH_COOKIE_SECURE=false`에서는 `project_llm_session` 쿠키에 `HttpOnly; SameSite=Lax; Path=/`를 적용한다. 이 설정은 LAN HTTP에서 로그인하기 위한 개발 설정이며 전송 암호화를 제공하지 않는다. HTTPS를 준비하면 `AUTH_COOKIE_SECURE=true`로 바꾸어 `__Host-session; Secure`를 사용한다. 전환 시 다시 로그인한다.

웹의 동일 출처 중계는 모든 POST의 `Origin`이 현재 웹 주소와 정확히 일치하는지 확인하고, `X-Project-LLM-Origin`을 서버에서 덮어쓴다. loopback 전용 FastAPI는 이 값과 Origin의 일치 및 허용된 로컬 주소 형식을 다시 검사한다. FastAPI를 외부 인터페이스로 열면 안 된다. 클라이언트가 제공한 신뢰 프록시 헤더를 그대로 전달하지 않는다. 인증된 상태 변경에는 세션에 연결된 CSRF 토큰도 요구한다. 로그인·가입에는 Origin·JSON 요청 검증과 요청 횟수 제한을 적용한다.

세션 원문, 비밀번호, CSRF 토큰을 로그에 남기지 않는다. 로그인 실패는 계정 존재 여부와 무관하게 같은 오류를 사용한다. 요청 횟수 제한은 현재 API 단일 프로세스 기준이다. 웹 중계의 연결 IP는 loopback으로 공유되므로 계정별 한도와 함께 전체 중계의 분당 30회 제한이 적용된다. 여러 기기를 개별 식별하는 제한은 아직 없으며, 여러 프로세스로 확장할 때 공유 저장소로 옮긴다.

## 초기 시스템 비밀번호

웹 공개 가입으로 시스템 계정의 비밀번호를 정하지 않는다. 로컬 운영자가 `scripts/manage_accounts.py set-password --email <계정>`을 실행하고 터미널의 숨김 입력에 새 비밀번호(8~32자)를 두 번 입력한다. 기존 활성 계정만 대상이며 시스템 권한을 자동 부여하지 않는다. 비밀번호를 명령 인자·환경변수·저장소 파일로 전달하지 않는다. 비밀번호를 잊었을 때도 이 로컬 절차로 변경한다.

## 채팅과 다음 단계

인증 도입 당시에는 저장·정산 연결 전의 일반 채팅을 차단했다. 이후 [ADR 0006](0006-persistent-chat-and-usage.md)에서 대화 저장·복원과 실제 사용량 정산을 연결했다. 현재 일반 계정은 유효한 기간 예산 안에서 채팅하며 시스템 계정도 실제 사용량을 기록한다. 기존 `/api/chat`은 `410`이고 저장형 생성 API를 사용한다.

## 검증과 롤백

임시 PostgreSQL에서 마이그레이션 왕복·스키마 비교, 비밀번호·세션 해시 저장, 24시간 경계, 철회·비활성화, 권한 분리, CSRF·Origin·쿠키 계약을 검사한다. 프록시의 쿠키 전달·SSE 취소와 프런트 인증 상태 전환도 별도 검사한다. 개발 DB에는 `upgrade head`만 적용한다.

`0004_auth_sessions`를 내리면 인증 수단과 로그인 세션이 삭제되므로 실제 DB에서는 백업·복구 계획 없이 실행하지 않는다. 기존 사용자·작업 공간·채팅·토큰 예산은 유지된다. DB를 비활성화하면 로그인·채팅은 사용할 수 없으며, 익명 채팅으로 자동 전환하지 않는다. 인증 코드와 스키마는 함께 유지하거나 함께 롤백해야 한다.
