# ADR 0015 — 압축 이전 원문 회수와 사용자별 장기 기억

- 날짜: 2026-09-12
- 상태: 구현
- 범위: 최우선 TODO 4번 + 5번, 3차 개발

## 문제와 결과

대화 압축은 원문을 보존하지만 요약에서 빠진 수치·식별자를 모델이 다시 볼 수 없었다. 새 대화에는 사용자가 저장한 이름·직업·선호를 전달할 저장소도 없었다. 압축 이전 원문을 현재 대화 안에서 제한적으로 회수하고, **설정 → 기억**에 사용자가 직접 관리하는 개인 기억을 추가한다.

## 사용자 동작과 저장

- 기억 이름 최대 80자, 내용 최대 500자, 사용자당 20개다. 같은 이름의 기억은 중복 생성하지 않고 기존 항목을 수정한다. 이름은 공백 정리·대소문자 정규화 후 비교한다.
- 기억은 `user_memories.user_id`로 격리한다. 서버 세션의 사용자만 결정권을 가지며 `system`도 다른 사용자의 기억을 읽거나 수정할 수 없다. 클라이언트의 사용자 ID·권한 필드는 거부한다.
- 자동 추출·자동 저장은 하지 않는다. 채팅에서 “새 대화에서도 기억해 줘”라고 요청하면 설정에서 직접 저장하도록 안내한다. 공유 대화의 발언을 개인 사실로 자동 저장하지 않는다.
- 목록·저장·수정·삭제는 CSRF·Origin·엄격한 JSON 검증과 `no-store` 응답을 사용한다. 프런트는 현재 컴포넌트 메모리에만 목록을 보관하며 화면 종료·계정 전환 후 늦게 도착한 응답을 버린다. 저장 중 중복 전송을 막는다.
- API는 목록의 `revision`을 변경 요청에 요구한다. 다른 탭·기기에서 수정한 뒤 옛 목록으로 저장하면 409로 거부하고 새로고침을 안내한다.

## 원문 회수

`context/recall.py`는 과거 내용을 묻는 표현이나 코드 식별자가 있는 현재 질문에서 최대 8개 검색어를 만든다. 현재 대화의 완성된 유효 요약 범위 이전 메시지 중 현재 답변 버전에 연결된 원문만 조회한다. 같은 작업 공간·대화·유효 생성 연결을 확인하며 교차 대화 검색을 하지 않는다.

SQL 부분 문자열 검색은 와일드카드를 이스케이프하고, 일치한 검색어 수·최근 순번으로 최대 24개 후보를 읽는다. DB 검색 제한은 1.5초다. 기본 최대 3개·합계 3,600자를 일치 구절 주변에서 발췌하며 원문 메시지는 변경하지 않는다. 회수 결과의 메시지 ID, 순번, 역할, 상태와 문자 시작·끝 위치를 `generation_runs.recall_sources`와 `meta.recall` 이벤트에 기록한다. 위치는 Python 문자열의 코드 포인트 기준이며 끝 위치는 제외한다. 발췌 본문은 관측 이벤트에 복사하지 않는다.

이 단계는 어휘 검색이다. 모호한 지시어나 의미만 비슷한 표현을 모두 찾는 의미 검색은 아니다. 관련 근거가 없으면 임의의 과거 사실을 만들지 않도록 모델에 안내한다.

## 문맥 구성과 외부 전송

실행 순서는 자동 압축 → 기존 웹검색 준비 → 로컬 원문·기억 반영 → 최종 답변이다. 개인 기억은 검색 판단·외부 검색어에 제공하지 않는다. 원문 회수 결과 역시 외부 검색이 끝난 뒤에만 추가한다. 현재 질문이나 최근 사용자 발언에 사용자가 직접 쓴 표현의 외부 전송 정책은 ADR 0014를 유지한다.

기억은 질문과의 어휘 관련성, 최근 수정 순으로 기본 합계 4,000자 안에서 선택한다. 서버 지침은 자료의 성격만 설명하고, 기억·회수 원문 자체는 별도 사용자 역할 JSON 참고 기록으로 넣는다. 자료 속 명령을 지시로 승격하지 않는다. 현재 사용자 요청을 우선하며 저장된 기억과 이전 기록이 충돌하면 현재 저장값을 사용하도록 안내한다.

참고 자료를 넣은 실제 tokenizer 입력량을 최대 5번 확인하면서 발췌·기억 개수를 줄인다. 전체 문자 한도, 모델 입력+출력 한도, 앞선 검색 판단 사용량을 뺀 잔여 허용량을 모두 검사한다. 참고 자료가 맞지 않으면 기존 질문·최근 문맥을 유지한다. 로컬 참고 자료는 실행 중 메모리에서만 추가하고 영속 요청에 개인 기억 원문을 복제하지 않는다.

`local_context`는 한 개의 로컬 도구 단계로 기록하며 별도의 생성 모델 호출은 없다. 원문 검색·기억 CRUD에 LLM 토큰을 청구하지 않는다. **최종 모델이 실제로 읽은 기억·발췌의 입력 토큰**은 기존 답변 사용량에 포함해 완료·중단 후 한 번 정산한다. 자동 요약의 시스템 유지 비용 면제와 시스템 계정의 예산 면제·사용량 기록은 유지한다.

## 수정·삭제가 파생 문맥에 미치는 영향

`users.memory_revision`은 실제 저장 변경마다 증가한다. 기억을 읽은 답변은 `generation_runs.memory_dependencies`에 사용자와 세대를 기록하고, 그 답변·요약을 참고한 후속 답변과 압축 요약도 같은 의존성을 이어받는다. 서로 다른 세대의 자료가 준비 중 섞이면 재요청하도록 거부한다.

기억이 바뀌면 이전 세대의 답변 본문을 다음 문맥·원문 회수에서 제외하고, 그 답변에서 파생된 압축 요약도 재사용하지 않는다. 유효한 사용자 원문을 다시 읽어 필요하면 압축한다. 이 정책은 수정뿐 아니라 삭제에도 적용되므로 캐시·요약에서 옛 기억을 되살리지 않는다. 보수적인 의존성 전파로 해당 기억과 무관한 내용이 함께 든 옛 답변도 재사용에서 제외될 수 있다.

이미 표시한 답변과 사용자가 직접 적었던 채팅 원문은 삭제하지 않는다. 기억 삭제는 채팅 이력의 영구 삭제가 아니다. 사용자가 옛 사실을 새 질문에 직접 제공하면 그 질문의 원문으로 남지만 개인 기억에 자동 재등록하지 않는다.

변경 중인 사용자의 대기·진행 작업과 그 기억에 의존한 공유 대화 작업에는 DB 중단 플래그를 설정한다. worker는 중단 및 실행 전 권한·세대 재검사를 수행한다. 이미 생성된 부분 답변과 확인된 실제 사용량은 기존 중단 정책에 따라 보존·정산한다.

## 설정과 API

| 설정 | 기본값 | 범위 |
| --- | --- | --- |
| `CONTEXT_RECALL_ENABLED` | `true` | 압축 이전 원문 자동 회수 |
| `CONTEXT_RECALL_MAX_RESULTS` | `3` | 1~5개 |
| `CONTEXT_RECALL_MAX_CHARS` | `3600` | 600~6000자 |
| `MEMORY_CONTEXT_MAX_CHARS` | `4000` | 500~8000자 |

- `GET /api/v1/memories` → `{revision, limit, items: [{id, key, content, updated_at}]}`
- `POST /api/v1/memories` → `{revision, key, content}`
- `PATCH /api/v1/memories/{id}` → `{revision, key, content}`
- `DELETE /api/v1/memories/{id}` → `{revision}`
- 변경 응답은 최신 목록·세대를 반환한다. 입력 오류 422, 다른 사용자 대상 404, 충돌·개수 초과 409, 인증 없음 401, CSRF·Origin 오류 403, 저장소 장애 503이다.

## 마이그레이션과 운영

`0014_memory_recall`은 기존 17개 테이블의 행을 유지하고 기억 테이블 하나와 세대·의존성·출처 필드를 추가한다. 현재 도메인·관측 테이블은 18개다. 기억 변경 이력이나 원문 회수 출처가 있으면 다운그레이드를 거절한다. 세대 검사를 제거한 이전 코드로 되돌리면 삭제한 기억이 파생 문맥에서 다시 사용될 수 있으므로 백업과 복구 정책을 먼저 마련한다. 데이터가 없는 격리 DB의 왕복은 지원한다.

2026-09-12 개발 DB의 진행 생성 0건을 확인하고 적용했다. 기존 17개 테이블의 행 수가 동일하고 신규 기억은 0건이며 `alembic check` 차이가 없다. 실행 중이던 PostgreSQL·웹·API·모델 서버는 유지했고 새 개발 서버나 원격 미리보기를 실행하지 않았다. API 경로와 웹 중계의 401/no-store 동작을 확인했다. 독립 worker는 코드 자동 reload가 없으므로 현재 앱을 재시작한 뒤 새 문맥 구성이 적용된다.

## 검증 범위

PostgreSQL 통합 검사는 기억 CRUD·CSRF·사용자/system 격리·개수 상한·동시 수정 충돌·DB 장애, 새 채팅 반영, 외부 검색 미전송, 입력 토큰 정산·멱등 정산, 수정/삭제의 후속 답변·요약 전파, 중단, 원문 출처·범위·다른 대화 격리·문맥 한도 생략을 다룬다. 프런트는 상태 경합·계정 전환·중복 저장·오류 복구·설정 탭 SSR을 검사한다. 전체 백엔드 657개 중 656개 통과 후 새 기본 필드의 기대값을 보정하고 관련 19개를 재실행해 모두 통과했다. 프런트 145개·TypeScript·lint·빌드도 통과했다. 실행 중인 개발 서버의 임시 합성 화면으로 추가·수정·삭제·초점 이동과 데스크톱·375px 배치를 확인하고 검증 파일·탭을 제거했다. 실제 모델 회상 정확도와 실제 계정의 전체 조작 평가는 자동 계약·합성 UI 검사와 구분한다. 상세 결과는 TODO의 3차 검증 기록에 남긴다.
